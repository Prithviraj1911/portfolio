Fixing broken links using Claude

A triage-first workflow for using Claude to separate real broken links from false positives in a Paligo debug report.

By Prithviraj Lahare2026

On this page

    Originally written for a documentation team's internal knowledge base. Resource IDs, UUIDs, and product names have been replaced with placeholders.

    Broken-link cleanup in Paligo can become a slow investigation, especially when the debug report mixes real issues with false positives. This guide describes a workflow that uses Claude to speed up that work, reduce mistakes, and focus attention on links that actually need fixing.

    The problem

    A Paligo Debug publish can flag 200+ links across 30+ topics in one publication. Investigating them by hand is slow and error-prone because of:

    • Volume: hundreds of links across dozens of topics.
    • Hidden location: the report often points to a container topic, while the real issue sits in a child topic three or four include levels deep.
    • False positives: Paligo flags cross-publication links when a subpublication is published on its own, and they look exactly like real errors.

    How Claude helps

    • Classification: sorts the report into glossary, image, HTML path, and UUID links.
    • Traceability: follows xi:include chains through nested topics to the real source.
    • Actionable fixes: decides real issue or false positive, and supplies corrected XML when needed.

    What you give Claude

    • The full broken-link report as text
    • The raw XML of a flagged topic, from Paligo's </> source view
    • A clear question or task

    What Claude gives back

    • A categorized, prioritized list
    • The exact line or topic to inspect
    • A verdict: false positive or real issue
    • Corrected XML when a fix is needed

    Workflow

    1. Start with the full debug report. Ask Claude to classify every entry and suggest what to investigate first.
    2. Prioritize UUID links. They're few and most likely to be real reference issues.
    3. Set aside likely false positives. HTML path links in subpublication publishes are usually noise.
    4. Open the flagged topic's XML in Paligo's source view and paste it into Claude.
    5. Ask Claude to trace the issue. For a container topic, it identifies the include chain to the real source.
    6. Confirm whether the target exists. If a urn:resource:component: target exists, it's usually a cross-publication false positive.
    7. Fix only what's confirmed. Paste corrected XML back into Paligo only for real issues.

    Prompts that worked

    Output quality depends on the prompt. Specific prompts with raw XML work much better than general descriptions.

    Prompt 1: Categorize the full report

    Here is the full broken link report from a Paligo Debug publish. Categorize every broken link as: glossary, image link, HTML path, or UUID link. Tell me which ones to fix first and which to skip for now.

    Result: all 222 links in one publication classified in one pass: about 15 glossary links deferred, about 40 image links flagged for media checks, about 160 HTML path links identified as likely false positives, and 3 unique UUID links prioritized.

    Prompt 2: Investigate a specific UUID link

    This is the source XML of topic <resource ID> (<topic title>). The broken link report flags it for <UUID>. Find the broken link and tell me exactly what to fix. [paste XML]

    Result: Claude identified the flagged topic as a container with no direct links, traced four levels of nested includes to the real source topic, confirmed the urn:resource:component: reference was correctly formed, and concluded it was a false positive. No fix needed.

    Prompt 3: Real issue or false positive?

    The report flags this UUID: <UUID>. I found the topic in Paligo and it exists. The source uses xlink:href="urn:resource:component:<id>". Is this a real broken link or a cross-publication false positive?

    Result: confirmed the URN format is correct for internal cross-references and that, with the target present, the report reflected publication scope, not a real break.

    What to fix first

    1. UUID links: few, and quick to validate as real or false.
    2. Image links: may mean missing or moved media.
    3. Glossary links: wait until the publication structure is stable.
    4. HTML path links: usually subpublication false positives.

    Time saved

    TaskWithout ClaudeWith Claude
    Categorize 222 broken links3–4 hoursAbout 10 minutes
    Trace a UUID link through nested includes30–45 minutes per link5–10 minutes
    Decide false positive vs. realManual XML reading, easy to miss contextNear-instant explanation
    Prepare corrected XMLHand-written, risk of syntax errorsExact replacement provided
    Outcome: Link investigation became a short triage-and-validate workflow. The biggest gain was avoiding edits to links that were never broken.

    Rules that make it work

    • Publish from the parent publication when running a Debug publish; a standalone subpublication inflates the report.
    • Give Claude raw XML from the source view. Specific input gets specific answers.
    • Skip glossary links at first. Handle them in a separate pass.
    • Don't edit valid urn:resource:component: links whose target exists.
