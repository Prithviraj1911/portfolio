Migrating MkDocs content to Paligo with a custom converter

A process guide for migrating MkDocs documentation into Paligo using a custom DocBook converter.

By Prithviraj Lahare2026

On this page

    Originally written for a documentation team's internal knowledge base. Company names, colleague names, and system identifiers have been removed.

    Scope: This process works for any MkDocs-based documentation set that needs to move into Paligo. It runs in parallel to an official migration pipeline: use it when you have the MkDocs source (or only the live site) but not the official converter scripts, or when you need to iterate on conversion logic yourself.

    Why this process exists

    Paligo is the target platform for the team's structured documentation. Content that lives as MkDocs Markdown on a separate static site needs to move into Paligo to gain consistent authoring, reuse, translation workflows, and one place for writers to work.

    The official pipeline depends on scripts and repository access that can take time to arrange. This process gives writers an independent path to real content in Paligo, using the same DocBook conventions so both approaches produce compatible results.

    What you get

    Real content imported into Paligo as a Publication with Topics, nested to match the source site's navigation, with images displaying correctly and procedures, notes, tips, warnings, and tables converted to native structured elements.

    What you don't get: Paligo reuse components. If the source shares content through an include directive, this process inlines that content into every page that uses it. The content is complete and correct, but duplicated rather than linked. Revisit it with the official pipeline's transclusion wiring if reuse matters.

    Prerequisites

    • Python 3 with pip available. Run python --version to confirm.
    • Access to the source content, either:
      • The MkDocs source folder (preferred, because it preserves the real source syntax), or
      • The live rendered site's base URL and navigation structure, to scrape as a fallback.
    • A Paligo account with import permissions.
    • A personal Paligo API key, only if you script anything beyond the import UI.
    • The converter scripts: a scraper (only if scraping), a navigation parser, and the DocBook package builder.

    A note on credentials

    Never hardcode a Paligo API token, user name, or password in a script or file. Set them as environment variables for the current terminal session instead:

    $env:PALIGO_INSTANCE = "your-instance-name"
$env:PALIGO_USER     = "your.email@example.com"
$env:PALIGO_TOKEN    = "your-api-token"

    These variables disappear when you close the window. If a token is ever exposed, regenerate it in Paligo immediately.

    Run the conversion

    Step 1: Set up your working folder

    Create one folder, for example C:\doc-migration, and put the three scripts in it. Run all commands from this folder.

    Step 2: Get the source content

    Option A: You have the MkDocs repository. Clone or extract it into the working folder so the .md files sit under their top-level area folders.

    Option B: You only have the live site. Install the scraper's dependencies and run it:

    python -m pip install requests beautifulsoup4 markdownify
python scrape_docs.py

    Check the scrape manifest to confirm zero missing pages or images. Option A converts more accurately, because it keeps syntax such as admonitions and includes that an HTML scrape can only approximate.

    Step 3: Build the navigation structure

    python -m pip install markdown beautifulsoup4 pymdown-extensions
python parse_toc.py

    This turns the site's indented navigation list into a structured file the converter uses for nesting. Confirm the reported page count matches what you expect.

    Step 4: Convert to DocBook packages

    python build_docbook_packages.py --docs <source-folder> --out paligo_import --combine

    --combine produces one file with everything nested correctly. Omit it to get one .zip per top-level area, which is useful for importing and checking a small area first.

    Then open paligo_import\build-manifest.txt and confirm every page converted with zero failures. Any failure is listed with its reason.

    Before you import: checklist

    Most import problems come from skipping one of these checks, not from the conversion itself.

    • The build manifest shows zero failed pages.
    • You know the deepest nesting level in your content, and will set Max folder levels higher than it.
    • You have confirmed the target folder in Paligo.
    • You have removed any previous test import of the same content. Reimporting creates duplicates; it doesn't update topics.
    • Your Paligo credentials are current and not exposed.
    • You've chosen which pages to spot-check: a table, a numbered procedure, a note or warning, and an inline image.

    Import into Paligo

    1. In Paligo, right-click the target folder and select Import content.
    2. Select the import type Docbook 5 (.xml).
    3. Click Select file and choose your .zip file.
    4. On the Custom options tab, set Max folder levels to the value from the checklist.
    5. Leave Folder numbering set to Enable if you want generated numbering such as 1.1 and 1.2.
    6. Click Ok. Large combined imports can take several minutes.
    Important: If Max folder levels is too low, Paligo can silently drop the deepest topics. Set it higher than you think you need; there's no downside.

    Verify the import

    • Pages nest under the correct parent, matching the source navigation.
    • Numbered procedures render as real steps, not plain paragraphs.
    • Notes, tips, and warnings render as distinct boxes, including inside a step.
    • Images display, including inline images in sentences, list items, and table cells.

    Clean up before re-running

    Delete the previous import's topics before importing again. If Paligo won't delete a topic, it's probably referenced elsewhere. Check its metadata for Reused here or Used in, remove those references, and try again.

    Source syntax the converter handles

    Source syntaxHow it converts
    !!! note, !!! tip "Title"Matching DocBook admonition (<note>, <tip>, <warning>, …) with the custom title when present.
    {% include "./_file.md" %}Snippet content is inlined into the page.
    Lightbox image macroStandard image, bundled into the package and referenced correctly.
    Glossary macroDisplay text only; glossary auto-linking isn't implemented.
    Numbered lists<procedure> and <step>; nested numbered lists become <substeps>.
    === "Tab name"Separate subsections headed by the tab name. Tab behavior is lost, but all content remains.
    ++key++<keycap>.

    Troubleshooting

    SymptomWhat to do
    python isn't recognizedReinstall Python with "Add to PATH" selected, then reopen the terminal.
    Missing module errorRun python -m pip install <package>.
    Pages failed in the manifestCheck the reason beside each page: usually a missing snippet, malformed syntax, or a converter bug.
    Deepest topics are missing after importRaise Max folder levels and import again.
    A topic can't be deletedRemove its reuse references first.
    Something was deleted by mistakeOpen Trash in Content Manager and select Put back, or drag the item back into a folder.

    Applying it at scale: inventory before you convert

    After validating the process on 150 pages, I applied it to a much larger legacy catalog of product plugin documentation. Before converting anything, I inventoried the Markdown source rather than the rendered site. The inventory changed the plan:

    FindingWhy it mattered
    470 Markdown files: 153 active, 316 archivedEarlier estimates were off by about 13 pages in each direction. Only the active set needed migrating.
    182 of 715 images under active pages were orphanedUnreferenced images were left behind instead of polluting the new media library; 533 were carried over.
    A third-party lightbox macro carried 532 of 576 image references (92%)The converter had to handle the macro itself; standard Markdown images were a rounding error.
    296 site-root absolute links had never been validatedThe source site's build ignored them, so every one needed explicit handling in the converter.
    15 "pointer stub" pages were near-identical boilerplateThey could be handled as one group, and later replaced by shared reuse components.

    The final build delivered 140 pages as DocBook packages, split by section to stay under the import size limit, with a taxonomy assignment for every topic and a redirect map covering every legacy URL. A small API script then replaced logo images in place, keeping each image's ID so no topic reference broke.

    Finding: A source inventory is the cheapest risk assessment in a migration. Every surprise above would otherwise have shown up as broken output after import.
