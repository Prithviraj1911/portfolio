AI-assisted structured documentation: Paligo + Claude

What happens when you treat an AI assistant as a production tool for structured content, and where the technical writer still has to decide.

By Prithviraj Lahare2026

On this page

    Based on documentation projects I led in 2026. Company names, product names, colleague names, and system identifiers have been removed. Time figures are measured or estimated from the work itself, as noted.

    Abstract

    Structured documentation platforms such as Paligo store content as DocBook XML. That structure makes reuse, translation, and multi-channel publishing possible, but it also makes cleanup, migration, and troubleshooting slow and error-prone when done by hand.

    Across four studies in 2026, I used Claude (in chat, and as Claude Code inside VS Code) to transform migrated XML topics, triage publishing errors, and migrate legacy Markdown documentation sites into Paligo. The studies also covered the review governance that keeps AI-assisted changes safe.

    ~6×faster per-topic XML cleanup (15–30 → 2–5 min)
    ~20×faster link-report triage (3–4 h → 10 min)
    150pages in the validated migration pipeline
    470source files inventoried for the next migration

    The headline finding is not speed alone. An AI assistant is most valuable when the writer turns tacit rules into an explicit specification, then applies it in separate, reviewable passes. Judgment about technical accuracy, information architecture, and cross-reference targets stays with the writer.

    Research question

    The documentation team was consolidating several products into Paligo. Content arrived from two directions:

    • Earlier imports that landed in Paligo with legacy markup: Markdown admonition markers, image placeholders, plain ordered lists instead of procedures, and inconsistent namespaces.
    • Legacy MkDocs sites still outside Paligo, with third-party macros, include snippets, and hundreds of unvalidated links.

    The question was practical: which parts of this work can an AI assistant do reliably, how much time does that save, and what process keeps the output trustworthy?

    Method

    1. A persistent prompt as a specification

    Instead of instructing Claude topic by topic, I wrote one standing project prompt with three rule groups: structural transforms, style rules, and table and image rules. Every topic in the session was processed against the same specification, so the twentieth topic got the same treatment as the first.

    2. Separate passes by dependency

    Changes with different dependencies were never mixed. Structural cleanup came first, cross-references second, and glossary wiring last, once the publication structure existed. Each pass was small enough to review on its own.

    3. Specific input, specific output

    Claude always received the raw source, such as XML from Paligo's source view or the full debug report as text, never a paraphrase. It returned paste-ready XML plus a short change summary, so review could focus on what changed.

    4. Human-in-the-loop review

    Every AI-produced change was reviewed by a writer before going back into Paligo. Large edits went through a branch and merge review (Study 4).

    5. Measurement

    Per-topic times compare manual cleanup estimates from the same content against timed AI-assisted cycles (paste, review, reinsert). Counts such as links, pages, and images come from reports and build manifests.

    Study 1: XML transformation at scale

    Problem. Hundreds of migrated topics needed the same family of fixes, at 15–30 minutes each by hand, with a real risk of malformed XML breaking publishing.

    Approach. The persistent prompt encoded:

    • <literal> → <code>; <orderedlist> → <procedure>/<step>
    • Legacy !!! note, !!! tip, and !!! warning markers → DocBook admonitions
    • Image placeholders → <mediaobject>; inline table icons → <inlinemediaobject>
    • Style: sentence-case headings, present tense, second person, no "please," "click" not "click on"
    MetricResult
    Topics processed50+ across user guide, how-to, and reference sections
    Effort per topic15–30 min manual → 2–5 min AI-assisted
    Structural XML errors introducedNear zero
    Publication-blocking SVG icons fixed8 (missing xmlns), re-uploaded in place so references stayed intact

    Study 2: Broken-link triage

    Problem. A Debug publish flagged 222 links across 30+ topics. Many were false positives caused by publishing a subpublication on its own, and real issues often sat three or four include levels below the topic the report named.

    Approach. Classify first, investigate second, fix last. Claude sorted the report by link type, then traced xi:include chains in the raw XML to the real source topic and decided whether each flag was real.

    CategoryCountDecision
    UUID links3 uniqueInvestigate first; traced and confirmed as false positives
    Image links~40Verify against the media library
    Glossary links~15Defer to the glossary pass
    HTML path links~160Publication-scope false positives

    Classification time fell from 3–4 hours to about 10 minutes, and tracing a link through nested includes from 30–45 minutes to 5–10. The bigger win was avoiding edits to links that were never broken. Full write-up: Fixing broken links using Claude.

    Study 3: Markdown to Paligo migration

    Problem. Legacy MkDocs sites needed to move into Paligo without waiting for the official pipeline's scripts and repository access.

    Approach. I built an independent pipeline that produces DocBook compatible with the official one, and ran it through Claude Code in VS Code:

    1. Source: the MkDocs repository (preferred) or a scrape of the live site.
    2. Navigation: parse the site's real navigation into a nesting structure.
    3. Conversion: build DocBook 5 packages, with admonitions, procedures, substeps, keycaps, tabs, and images mapped to native elements.
    4. Gate: a build manifest with zero failures and a pre-import checklist (Max folder levels, target folder, no duplicate imports).
    5. Verify: spot-check a table, a procedure, an admonition, and an inline image.

    Validation. A full 150-page migration of real product content imported with correct nesting and formatting.

    Scale-up. Before converting a larger legacy catalog, I inventoried its Markdown source:

    Inventory findingConsequence
    470 Markdown files: 153 active, 316 archivedScope fixed to the active set; earlier estimates were off by about 13 pages each way
    182 of 715 images orphanedOnly the 533 referenced images were carried over
    A lightbox macro carried 532 of 576 image references (92%)The converter handles the macro directly
    296 site-root links had never been validatedExplicit link handling built into the converter
    15 near-identical "pointer stub" pagesHandled as a group, with shared reuse components for licensing and support text

    The final build delivered 140 pages, split by section to stay under the import size limit, with a taxonomy assignment for every topic and a redirect map covering every legacy URL. A small API script replaced logo images in place, keeping each image ID so no topic reference broke.

    Study 4: Review governance with branching

    Faster changes need a safer review path. I wrote the team's Paligo branching guide so that AI-assisted and manual edits follow the same controls:

    • One branch per change request, labeled with its ticket number.
    • Work stays in the branch; the published topic stays untouched.
    • The reviewer, not the author, merges, after checking the change against the ticket.
    • Merge previews are reviewed change by change; unused branches are deleted.

    Full guide: Paligo branching: tips and tricks.

    Findings

    1. Consistency beats speed. The biggest benefit is that every topic gets identical treatment, whatever its complexity, or the writer's fatigue or time of day.
    2. Write the rules down. The prompt is a specification. Making tacit style and markup rules explicit improved the output and also documented the team's standards.
    3. Separate passes by dependency. Mixing structure, links, and glossary work multiplies failure modes; separating them keeps each review small.
    4. Raw source in, paste-ready output back. Specific XML gets specific answers; paraphrased descriptions get generic ones.
    5. Triage before repair. In error reports, most of the volume can be noise. Classifying first prevents unnecessary edits.
    6. Inventory before migration. A source audit is the cheapest risk assessment. Every surprise it found would otherwise have appeared as broken output.
    7. Preserve identity. Replacing assets in place (same ID) rather than re-uploading keeps every reference intact.

    Limitations

    • Claude can't judge whether well-formed content is technically or architecturally correct.
    • It can't reliably choose a new cross-reference target when the correct one is unknown.
    • It doesn't make content strategy decisions: scope, information architecture, or reorganization.
    • Claude Code can't operate the Paligo browser UI; imports and publishes stay manual, with Claude guiding.
    • Manual-time baselines are estimates from the same content, not a controlled experiment.
    • Credentials must stay in environment variables, never in prompts, files, or scripts.

    Playbook for teams

    1. Write a persistent prompt that encodes your style guide, voice, and markup conventions. Share it as a team library.
    2. Split work into passes: structure → cross-references → glossary.
    3. Feed raw source; ask for paste-ready output and a change summary.
    4. Triage error reports by category before investigating individual items.
    5. Inventory any source before migrating it; gate imports on a zero-failure manifest.
    6. Route changes through branches; the reviewer merges.
    7. Measure before and after, so the value is visible to stakeholders.
    Bottom line: Claude was a force multiplier. It removed the mechanical burden so writing expertise could stay on accuracy, structure, and the reader.
