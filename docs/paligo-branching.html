Paligo branching: tips and tricks

A team guide to branching and merging topics in Paligo.

By Prithviraj Lahare2026

On this page

    Originally written for a documentation team's internal knowledge base. Team names have been removed.

    Branching creates a connected copy of a topic or publication. Unlike a standard copy, the branch stays linked to the original, so you can compare versions and merge selected changes back later.

    Think of a branch as a safe workspace: the main topic stays unchanged and publishable while edits, review feedback, and experiments happen in the branch.

    Quick rule: Always include the ticket number in the branch label, for example DOC-123 – Update tile config wording.

    When to branch

    • Reviewing edits with an SME or peer before they go live
    • Testing a restructure or major rewrite without risking published content
    • Working on one change request in isolation
    • Managing parallel content for different releases or product variants
    • Supporting translation or localization in progress

    Create a branch

    1. In Content Manager, find the topic or publication.
    2. Click the … menu next to it.
    3. Select Branching > New Branch.
    4. Enter a branch label.
    5. Optional: select Select location for new branch to store it in another folder.
    6. Optional: select Open new branch in editor to start editing immediately.
    7. Click Create.

    Work in a branch

    • Edit the branch like any topic; the editor is the same.
    • The main topic stays untouched while you work.
    • You can have several branches of the same topic at once.
    • Use compare or preview to review differences before merging.

    Merge a branch

    1. Make sure the main topic and the branch are both checked in and set to Work in Progress.
    2. Click the … menu on the branch to merge from.
    3. Select Branching > Merge Branch.
    4. Choose the merge target, usually the main topic.
    5. Optional: select Change release status and check in.
    6. Review the differences: green shows additions, red shows deletions.
    7. Accept or reject individual changes.
    8. Click Preview to confirm the result, then Close.
    9. Choose whether to delete the branch after merging.
    10. Click Merge.

    Tips

    • Keep branch structures simple; nested branches are hard to manage.
    • Update the label if the ticket scope or status changes.
    • Use branches for SME review so comments don't affect live content.
    • One branch per change request keeps review, merge, and traceability predictable.

    Who merges

    The person who created the branch doesn't merge it. The reviewer or approver does, after the final review. Before merging, the reviewer:

    1. Reads through the content changes in the branch.
    2. Checks that the branch label references a ticket number.
    3. Opens the ticket and confirms the requested change matches what was done.
    4. Confirms the ticket status shows the change is approved and ready.
    5. Only then merges the branch into main.
